Key cost drivers in the original model were: (1) an unbounded payment loop that can trigger repeated handling; (2) early and costly escalation to credit collection before attempting low-cost collection; (3) separate manual steps for notification and penalty; and (4) the possibility of creating a fine but skipping sending it, which wastes effort. The redesigned model reduces execution cost by: 
- Consolidating front-end steps: Create Fine, Send Fine, and Insert Fine Notification are merged into a single Issue Fine activity. This removes handoffs and avoids the wasteful path where a fine is created but not sent. Notification is assumed to be automated within Issue Fine.
- Bounding rework: The unbounded payment loop is replaced with an XOR between a single payment attempt and a two-attempt sequence. This caps handling effort while still allowing a reasonable retry.
- Deferring and gating costly steps: Add penalty and Send for Credit Collection are moved into a late, optional escalation branch that is reachable only after payment attempts. This prevents premature escalation fees and avoids penalty work for cases that pay during the attempts.
- Simplifying control flow: The final model uses one top-level partial order with XOR children, avoiding nested partial orders and unnecessary optional branches, which reduces complexity and the likelihood of costly exception handling.
Collectively, these changes cut manual touches, cap repeated work, and minimize external collection costs, while keeping a feasible, compliant flow for fine processing.
