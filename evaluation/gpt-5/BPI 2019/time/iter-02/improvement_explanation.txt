What slowed the process down in the original model was the sequential top-level wiring: after Create Purchase Order Item, the flow waited for the optional Receive Order Confirmation, then for a block that bundled Record Goods Receipt and Vendor creates invoice, and only afterwards could the optional invoice-processing chain (Record Invoice Receipt -> optional Remove Payment Block -> Clear Invoice) start. This serialized independent work and delayed downstream activities unnecessarily. Improvements implemented to reduce execution time: 1) Remove unnecessary sequencing barriers by running independent branches in parallel right after PO creation. Specifically, Receive Order Confirmation (optional), Record Goods Receipt, Vendor creates invoice (optional), and the optional invoice-processing chain are all triggered directly from Create Purchase Order Item. This allows invoice receipt and payment processing to proceed as soon as the invoice arrives, without waiting for goods receipt or order confirmation. 2) Flattened the intermediate partial order that only grouped Record Goods Receipt and the optional vendor event; these are now top-level concurrent nodes. This eliminates an artificial synchronization point and exposes concurrency. 3) Kept the internal invoice-processing logic intact (Record Invoice Receipt precedes optional Remove Payment Block and then Clear Invoice) inside an optional XOR branch, so when there is no invoice the entire branch can still be skipped. This preserves feasibility while enabling earlier start of invoice handling. Together, these changes remove gating, allow earlier execution of downstream tasks, and shorten end-to-end lead time without changing core business rules or adding rework.
