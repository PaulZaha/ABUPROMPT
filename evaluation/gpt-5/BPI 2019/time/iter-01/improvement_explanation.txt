What I changed and why it reduces execution time:
- Decoupled Receive Order Confirmation from downstream steps. In the original model, Create Purchase Order Item -> Receive Order Confirmation gated the entire flow to goods receipt and invoicing. I moved Receive Order Confirmation to be optional and concurrent after PO creation. This removes an artificial waiting point and allows logistics and finance to start immediately, shortening end-to-end time.
- Enabled early invoice processing in parallel with delivery. Originally, invoice processing (recording the invoice and clearing) could only start after the combined goods receipt/vendor steps finished. I restructured so that Record Invoice Receipt can start right after PO creation (i.e., as soon as the invoice arrives), overlapping with goods receipt. This reduces the critical path duration to payment.
- Preserved financial control while optimizing flow. Clear Invoice now has explicit prerequisites on both Record Invoice Receipt and Record Goods Receipt, and (if applicable) Remove Payment Block. This ensures payment cannot clear before goods are received, while still allowing invoice recording and any block-removal preparation to happen earlier. Remove Payment Block remains optional and is only reachable after invoice receipt.
- Flattened the structure to a single partial order (no nested partial orders as gating constructs). This makes dependencies explicit and avoids implicit bottlenecks from nested partial orders.
- Simplified the role of Vendor creates invoice to an optional, independent event (for tracking/telemetry). It no longer gates invoice processing, which is triggered by the actual arrival/recording of the invoice, reducing unnecessary waiting time.
Assumptions/feasibility notes:
- For invoiceable purchases, invoice recording is expected; for non-invoice scenarios (e.g., free-of-charge), model this as a separate variant. Many ERP setups (e.g., SAP with GR-based IV) allow posting the invoice early with a default payment block and clearing only after GR, matching the redesigned dependencies.
Net effect: less idle time and more parallelism without paying early. The process finishes faster because invoice verification and block removal prep run concurrently with logistics, and order confirmation no longer delays subsequent work.
