The original model exposes a key risk: Create Purchase Order Item is the first activity and there is no gate or control step to detect duplicates before creating a new order item. This allows multiple users or automated triggers to create the same order item concurrently or repeatedly, resulting in duplicate orders. To directly prevent duplicates, I added two controls before creation: (1) a Duplicate Order Check, which programmatically searches for existing open purchase orders/items for the same supplier/material/need and decides whether to proceed with creation or reference an existing order; and (2) a short, technical creation lock around the decision to eliminate race conditions where two actors attempt to create the same item at the same time. The process then branches using an XOR: if no duplicate is found, it proceeds to create the PO item; if a duplicate is detected, it references the existing order and does not create a new item. To ensure the lock is held only for the minimum time needed and does not block downstream activities, I release the lock immediately after the create/reference action within each branch, before continuing with the rest of the procure-to-pay flow in the non-duplicate branch. The remainder of the process (order confirmation, goods receipt, invoice handling, payment unblocking, and clearing) is unchanged and only occurs on the non-duplicate branch, ensuring no downstream work is performed for duplicates. This redesign prevents duplicate orders by enforcing a pre-creation duplicate check and by making creation mutually exclusive (via a lock and XOR routing) with the duplicate handling path.
