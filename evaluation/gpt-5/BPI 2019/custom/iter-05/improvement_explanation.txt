Duplicates typically occur when multiple users create PO items for the same requisition/vendor/material in parallel or when a prior PO already exists but is not visible at creation time. To prevent this, I added a mandatory system check before any PO creation and a hard lock immediately after creation. Specifically: (1) A required "Check for Duplicate PO" activity gates the flow. It feeds an XOR: either proceed to creation if no duplicate is found or route to a "Log Duplicate and Notify Requester" path that aborts creation. This guarantees PO creation cannot happen without a duplicate check. (2) After successful creation, an "Apply PO Creation Lock" activity ensures the originating requisition or reference is locked to prevent subsequent attempts from creating additional POs for the same item. This addresses concurrent creation risks. (3) I streamlined the downstream flow so invoice processing only occurs when the vendor actually creates an invoice; the invoice chain is made optional and internally sequences vendor invoice -> invoice receipt -> optional payment block removal -> clear invoice. Goods receipt can happen in parallel with invoice processing, after the optional order confirmation step. The redesign avoids nesting partial orders inside partial orders in the final model and ties optional branches more cleanly, improving correctness and making the duplicate-prevention steps feasible in typical ERP settings (e.g., SAP: duplicate check via search/match and PR/PO locking via status or custom control).
